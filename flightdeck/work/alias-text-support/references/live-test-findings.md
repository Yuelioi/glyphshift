# Qt Quick 实际测试与剩余问题

## 原生接入进度

已实现独立 Qt Quick 原生包并接入 Runtime Bundle。5 项状态合同、1 项使用授权 Qt 库的合成原生合同及严格 Clippy 通过；合成合同明确验证控制线程退出后仍可激活、更新与恢复。真实 Alias 的原生主界面、文件菜单循环及 Tooltip 分项通过；悬停测试中的焦点、欢迎页同名按钮和提示自动关闭影响已与产品行为区分。

用户随后明确要求停止逐项自动实机测试，交由自己在 App 中验收。已使用规定的同步构建入口构建并启动测试版 App，生产 Loader 对 11 个 Adapter 及打包副本验证通过。用户已重启后在 App 中手动测试，并明确确认没有问题、要求提交。该验收限本轮版本与场景，不扩展为所有界面或所有软件版本均已支持。

## 用户确认的优先级

可用优先，必要时可以要求重启软件。晚附加不是支持前提。用户随后明确当前已重启且没有任何工程，授权后续直接验证、必要时重启。实验仍不把用户输入或工程数据当成 UI 文案替换，也不推广这一空工程授权到其他实例。

## 最新结论：真实目标通过

用户重启后，以 `exceptions: propagate` 的桥接重新注入真实 Alias，单个控制面板标题先通过，再完成主界面、动态菜单和实际 Tooltip 的组合验收。没有修改安装目录、全局字体配置、QPA 后端或工程内容；测试结束恢复原文并卸载桥接，进程保持响应。

动态验证证明：先启用翻译再打开文件菜单能自动替换；菜单连续 5 次关闭重开，每次替换及恢复通过；Tooltip 首代、第二代、恢复以及移开后重新悬停通过。宿主绑定、翻译对象销毁及恢复最新宿主原文由此前合成合同覆盖，没有将合成覆盖冒充真实 Alias 全部行为。

最终运行仓库 Playwright test runner，真实行为组合验收 1 项通过，读取三组渲染截图的像素验收 1 项通过。测试期间遇到的菜单定位失败已修正：弹出窗口可能成为 Windows 报告的主窗口，必须通过实际主界面对象识别正确窗口；不能把旧主窗口句柄当成稳定产品身份。

短暂文字必须检查实际透明度和像素：`Maximize` 文字对象虽 `visible` 为真，但实际透明度为零，未计入 Tooltip 成功证据。最终采用真正显示的 `Multi Color` 提示，译为中文并核对像素。

当前结论为 **真实 Alias 上的 Qt Quick 实验性原位翻译可行**，不是已发布的产品支持。Frida 仍仅为本地实验工具；下一步需要生产原生 Adapter、版本/符号门控、线程与销毁合同、Runtime 生命周期和包加载验收。

## 真实 Alias 观察

通过进程内实验桥接，在目标窗口线程的消息分发边界枚举 `QGuiApplication::allWindows`，筛选 `QQuickWindow`，由 `contentItem` / `childItems` 取得 Quick 视觉树，再对 `QQuickText` 读取完整文字。

该次快照得到 13 个窗口、3,234 个 Quick 项目、174 个文字项，其中 80 个带可见标记且文字非空。采集包括顶部菜单、工具分类与控制面板。Qt `visible` 不能证明没有遮挡、裁剪或超出当前屏幕，所以此计数不等于屏幕覆盖率。

## 首轮真实写回失败与修正

首轮 `QQuickText::setText` 中文写入抛出实验桥接的 native system exception；复测后 Alias 持续无响应。结束本轮测试控制进程后目标仍未恢复，没有强制终止 Alias。已请用户处理工程保存/恢复及重启。

线程采样显示主线程等待 DirectWrite 字体查询，调用链经过 `QWindowsDirectWriteFontDatabase::populateFamily`、fallbacks、`QFontEngineMulti` 与 `QTextEngine::shapeText`。这只能定位挂起阶段，不能证明 Qt 或 Alias 自身存在独立缺陷。

实验工具的 `NativeFunction` 默认使用 `exceptions: steal`，会把原生异常转成 JavaScript 异常并可能使宿主进入未定义状态。桥接切换 `exceptions: propagate`，让宿主处理原生异常；用户重启后真实目标验证全部通过。没有在健康目标上重新引入错误方式做破坏性 A/B，因此将其记录为得到后续结果支持的解释，不声称已证明唯一根因。[Frida 官方 API](https://frida.re/docs/javascript-api/#nativefunction)

Qt 6.8 官方确认 Windows 默认字体后端已改为 DirectWrite；旧 GDI 后端仍可通过 QPA `fontengine=gdi` 参数启用。后者只作为必要时的独立启动对照实验，不是已交付或已验证的 Alias 解决方案。[Qt 6.8 更新说明](https://doc.qt.io/qt-6.8/whatsnew68.html)

## 合成目标通过的证据

实验宿主使用 PySide6 6.8.3 创建纯合成 QML 场景，并显式预加载授权目标所带 Qt 库、匹配的平台插件和 QML 导入目录；未复制或修改目标安装内容。

经仓库 Playwright test runner 运行本地实验验收，最终 1 项完整场景通过，包含：

- 8 个静态文字项首代中文替换、第二代中文更新及原文恢复。
- `QQuickWindow::grabWindow` 获取真实渲染图像，避免 GPU 窗口的 PrintWindow 黑图和前台遮挡误判。
- 首代与原图有 9,466 个像素超过差异阈值；第二代与首代有 896 个；恢复后与原图差异为 0。人工看图确认中文正常，计数仅属于该合成场景。
- 宿主源属性更新后 QML binding 仍重新计算，不被旧译文快照当成新原文覆盖。
- 动态文字创建后可翻译；销毁已翻译对象后可安全恢复其余对象。
- 停用恢复宿主最新原文，而不是最初旧原文。

这些是合成 seam 合同，不是 Alias 的真实写回验收。全部脚本、依赖、目标描述、日志、图片和原始文字仅保留在本机忽略的测试区域，不作为仓库必需资源。

## 生产实现前的剩余边界

1. 用原生 Adapter 实现相同 seam，并为线程调度、Qt 版本/符号匹配、原文状态与停用恢复建立确定性合同；本地实验中的约 250 毫秒扫描不是已完成性能验收的调度设计。
2. Qt 视觉树之外的业务数据不纳入替换；`QQuickTextInput` / `QQuickTextEdit` 不因存在 text 属性而被默认写入。
3. 对 QObject 寿命、宿主 binding 重算、动态原文更新、富文本和长中文布局保留明确边界，不由本轮少量标签推导全应用兼容性。
4. 将真实验证移接到生产 Runtime 与标准发布代次后再进入产品 Catalog；本轮没有构建桌面 App 或修改 Runtime Bundle。
5. 如其他版本或冷启动状态需要启动时接入，可以要求用户重启；当前版本本轮已经证明重启后的运行中附加可用。
