# 桌面 UI/UX 一致性基线审计

## 结论

Glyphshift 当前不需要重做 UI 架构。应用框架、管理页头、详情头、表格框架、配置分组、危险确认和
深浅主题已经形成稳定体系；主要问题集中在共享组件之外的局部实现，以及这些局部实现在紧凑窗口、
键盘操作和普通用户术语下造成的体验分叉。

综合 Nielsen 评分为 **26/40（Acceptable）**。产品信息模型和安全反馈明显高于通用后台，但紧凑
表格上下文、功能性小字、动作层级、技术术语与键盘效率仍需在发布前系统修复。

## 方法与证据边界

- 独立设计评审覆盖四类管理列表、四类详情/编辑、Settings、Help、深浅主题、1440×900 与
  960×640，并验证空态、确认态和代表性键盘路径；本地 Playwright 评审 3/3 通过。
- 独立机械检查对 `apps/glyphshift-desktop/src` 运行一次 Impeccable detector，结果为 0 findings；
  这只证明没有命中已知静态反模式，不代表运行时布局无问题。
- 机械浏览器检查完成 Workflow 列表/详情的宽窄证据与 Settings 浅色宽屏证据，随后因审计 harness
  超时而有界终止。Help 浏览器注入、紧凑 Settings 几何统计和全量点击目标统计未完成，不能标为通过。
- 所有截图、trace、临时配置和原始日志只保存在 `local-test/`；本文只记录可移植结论。

## 已经做对的部分

1. Workflow、Software、Dictionary 与 Probe 的对象边界清楚；启用期望和实际 Runtime 状态没有混为一谈。
2. 管理页头、详情头、表格、表单分组、分页、空态和确认对话框形成了可学习的跨页语法。
3. 未保存保护、软件预检、Probe 暂停/释放/清理和危险确认提供了可信的高风险反馈。
4. 深浅主题不是简单反色，主要层级和主动作在两套主题中保持一致。

## 优先问题

### P1 — 紧凑表格丢失对象身份与行级动作

Workflow 表使用 1080px 最小宽度；960px 下操作列不在首个可视区域。键盘聚焦右侧动作时浏览器会把
表格横向滚动到操作列，名称与选择框随即离开视口，用户必须记住自己正在操作哪一行。其他集合页也使用
不同的固定最小宽度，因此需要一套跨表格策略，而不是只修 Workflow。

修复方向：定义列优先级；固定选择列与对象身份列；把次要摘要折入身份单元格或行详情；超过三个的
行级动作进入带文字的 overflow；紧凑宽度保留主要编辑入口并给出明确横向溢出提示。键盘焦点移动后，
对象身份必须仍然可见。

### P1 — 9–10px 功能性文字形成全局可读性门槛

当前组件模板中 9px 文本约 60 处、10px 文本约 39 处。页头说明、状态解释、字段帮助、错误恢复和
表格次级信息都使用了这一档，它们并非可忽略装饰。浅色主题和长时间使用时最明显。

修复方向：先建立语义 type tokens；功能性 metadata 基线提高到 11px，说明正文提高到 11–12px 并
增加行高；仅短计数或非关键标签保留 10px。用 100%、125% 与 200% 文本缩放和两主题验证，避免用
增加字重掩盖字号过小。

### P2 — Probe 详情头混合当前任务、增强能力与生命周期治理

运行软件、AI、保留、结束并清理、暂停/继续在详情头并列；紧凑宽度下标题上下文先被压缩。临时词典
同时暴露机器生成名称，用户会在最敏感的清理决策旁看到无法解释的内部身份。

修复方向：详情头只保留与当前运行状态一致的主要动作；AI 靠近翻译表工具栏；“保留 / 结束并清理”
进入明确的临时任务菜单或危险区；临时词典始终显示人类名称与“临时”徽标，内部 ID 不进入普通界面。

### P2 — Help 以实现目录而非恢复任务组织

Help 的七列 Adapter 表在紧凑窗口需要横向探索，长 Technology 值会与相邻动作争夺空间。它能列出
能力，却不能直接回答“软件未启动”“权限不匹配”“没有捕获到文字”等最常见问题。

修复方向：先提供问题到恢复动作的任务入口，再展示 Adapter 详情；把名称/说明、适用技术、能力收敛
为两到三块，版本和配置进入展开详情。不可避免的 Adapter/Runtime 术语提供一句任务化解释。

### P2 — 键盘入口成本与 heading 语义仍不完整

内容主动作前需要穿过整条标题栏焦点序列；Workflow 详情的 accessibility tree 从 h1 直接进入 h3。
这不会阻断鼠标流程，但会降低熟练用户和辅助技术用户的效率。

修复方向：增加跳到主内容/页面工具栏的键盘路径与可发现加速器；保持 `h1 → h2 → h3`；为多工具栏
提供可访问名称，并把同类 Esc/焦点恢复行为加入共享合同。

## 推荐实施顺序

1. **紧凑集合与键盘上下文：** 先修共享表格策略、行级动作与内容跳转。这是最明确的 P1，且会影响
   Workflow、Software、Dictionary、Probe 与 Help。
2. **语义字体阶梯：** 在共享页头、表格次级信息、配置说明和状态解释中落地 type tokens，再处理局部例外。
3. **Probe 动作与普通用户命名：** 收敛详情头，移除机器名，重排 AI 与生命周期动作。
4. **任务型 Help 与语义收口：** 重组帮助信息并修复 heading、toolbar label 和剩余键盘路径。

每批修复都应同时覆盖代表性宽/窄、深/浅和中英文，不按单页截图逐个打补丁。

## 外部校准

- [Fluent 2 Layout](https://fluent2.microsoft.design/layout) 强调一致 spacing rhythm 与响应式信息关系。
- [Fluent 2 Typography](https://fluent2.microsoft.design/typography) 为 Windows 提供稳定语义字号阶梯，并把
  可读性与对比度作为字体决策的一部分。
- [Fluent 2 Toolbar](https://fluent2.microsoft.design/components/web/react/core/toolbar/usage) 要求工具栏单行、
  空间不足时进入 overflow，并把危险动作与普通动作分组。
- [Carbon Data Table](https://carbondesignsystem.com/components/data-table/usage/) 建议选择后显示批量动作栏，
  并在超过少量行级动作时使用 overflow 减少持续噪声。
- [Cloudscape Table View](https://cloudscape.design/patterns/resource-management/view/table-view/) 明确区分空集合、
  无匹配、加载与错误，并把恢复动作放在状态附近。

## 残余风险

- 本轮没有验证真实 Windows 系统缩放、UAC、屏幕阅读器或 Runtime 错误时序。
- 机械浏览器证据为代表性而非全量；Help、Settings 紧凑几何和点击目标尺寸仍需在对应修复 Slice 中补测。
- Detector 零命中不能替代运行时可用性测试；后续仍以仓库 Playwright 和真实桌面复核为准。
