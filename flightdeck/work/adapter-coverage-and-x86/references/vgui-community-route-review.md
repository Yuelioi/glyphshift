# VGUI / Source 社区调研与路线复核

调研日期：2026-09-08。用户要求先查社区和网络，停止围绕现有实验反复修补。本轮仅阅读公开资料及现有工作记录，未操作目标、运行第三方程序或修改功能代码。链接为阅读时的分支页面，不能替代目标二进制的版本验证。

## 结论

**建议暂停扩展逐字绘制重放，优先评估本地化查询与控件完整文本入口。** 共用 Core 机制可保留；没有证据要求为了保持通用性，必须从最低层字形重建所有界面。

成熟项目把提取整理和原位写回分开：Textractor 的上下文缓冲不能充当原位替换证明；Luna 单独定义内嵌能力；XUnity 依靠控件文本及生命周期。详见 [三个项目的源码对比](community-hooking-patterns.md)。这是对现有路线的复核，不是已经找到可直接复制的 VGUI 适配器。

## 1. 社区修改 Source 文本优先寻找本地化资源

Steam 的一则求生之路文字修改讨论中，提问者在 2024 年亲自确认：改错资源时没有效果，改用另一份本地化资源后成功。回复和提问者还指出资源覆盖、文件名称及加载位置不同。这是一次具体通知文字的用户验收，不能推广为所有菜单、任意 VPK 或当前版本的通用保证。[原始讨论及提问者确认](https://steamcommunity.com/app/550/discussions/0/2765630416811369888/)

**推断：** 首先核对文字究竟来自哪个加载源，通常比观察最终字形更有信息量。社区的文件修改操作只是路线参考，不意味着 Glyphshift 应直接修改用户安装文件；本轮没有执行资源替换。

## 2. 框架有完整字符串查询接口，不只提供逐字绘制

AlliedModders 维护的 `hl2sdk/l4d2` 分支公开 `ILocalize`：含 `Find`、`FindIndex`、`GetValueByIndex`、格式化字符串构造和资源加载。它还提供遍历、`SetValueByIndex` 等编辑方法，但头文件明确将相关一组方法定位为本地化编辑器用途。这证明存在语义层候选入口，不证明能在任意目标或线程直接调用编辑方法。[l4d2 ILocalize.h](https://github.com/alliedmodders/hl2sdk/blob/l4d2/public/vgui/ILocalize.h)

Valve 的公开 TextImage 实现显示：带本地化标记的文本先查询 token/index，再交给 Unicode SetText；后者复制文字并标记重新计算截断。**修改查询结果不会自动等价于更新所有已存在控件的副本。**[TextImage::SetText](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/vgui2/vgui_controls/TextImage.cpp)

Label 的公开 SetText 则除了更新 TextImage，还调用布局失效和重绘；源码也说明设置文字并不自动设置标签尺寸。因此控件更新、布局及字体必须一起验收。[Label::SetText](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/vgui2/vgui_controls/Label.cpp)

**推断：** 应比较“在复制到控件前替换查询结果”和“通过可信的控件入口更新文字”两条路径。仅 Hook `Find` 也不充分：有调用者直接使用 index，格式化文本还有独立构造入口。热启用、换代、停用都需要处理已经缓存的文字；必要时界面重建或重启是可接受的候选策略，但本轮没有证明该目标的具体重建方式。

## 3. Source 分支差异是实质差异

社区 SDK 单独维护 l4d2 分支。对比该分支和 Valve SDK 2013 的 Surface 头文件，`CharRenderInfo` 的成员顺序和顶点存储方式不同：一方内嵌顶点数组，另一方使用顶点指针；方法集合也有差异。这些是源码中可见的接口差异，不应凭一个相同技术名就视为统一 ABI。[l4d2 ISurface.h](https://github.com/alliedmodders/hl2sdk/blob/l4d2/public/vgui/ISurface.h)、[Valve SDK 2013 ISurface.h](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/public/vgui/ISurface.h)

另一个社区客户端工具 ValveEXE 自己明确列出因引擎差异而不支持 Left 4 Dead 2。该工具不是翻译器，因此这只能作为“Source 家族支持不能自动泛化”的旁证，不是 Glyphshift 无法支持的证据。[ValveEXE 自身文档](https://pysourcesdk.github.io/ValveEXE/)

**推断：** 一个逻辑 Adapter 可以维护经过验证的框架版本能力。通用性不要求所有版本共用一套虚表/结构体，更不需要把某游戏的菜单词句硬编码进实现。当前实验已有 ABI 检查，但栈清理正确不等于完整绘制语义已覆盖。

## 4. 路线优先级

以下为结合一手资料与当前未完成实机证据的工程判断，不是兼容性承诺。

| 候选 | 优先级 | 主要收益 | 需要先回答的问题 |
| --- | --- | --- | --- |
| 本地化资源加载/查询层 | 首先评估 | 取得 token、整句和格式化变量，不必追踪每个字形 | 实际使用哪个接口版本/查询入口？返回内存谁持有？既有控件如何刷新或重建？ |
| 可信控件 SetText / 文字所有者 | 其次评估 | 由原框架重新布局并绘制，可设计原文快照和恢复 | 能否可靠发现活对象及可调用入口？线程与对象销毁如何处理？不能用猜测的私有字段替代这些条件 |
| 公开完整绘制调用 | 限定范围保留 | 对真正使用该调用的文字可复用现有 Core | 是否属于当前可见绘制？是否存在缓存、其他路径或后续覆盖？ |
| 逐字调用延迟重放 | 实验后备 | 在边界和状态均可靠时处理自绘文字 | 需承担字体、光标、透明度、裁剪、嵌套和提交顺序；当前成本与实机证据不匹配 |
| 修改语言文件或覆盖层 | 不作为默认替代 | 社区确有这些独立解决办法 | 文件冲突、更新及恢复与覆盖层产品语义都需另行设计；用户没有要求改变本项目的原位替换目标 |

## 5. 对当前工作的处理

- 保留共用完整性、可选 Host 和 Qt/DirectWrite 的已测实现，按 [改动整理](implementation-review.md) 单独审阅。
- VGUI 保持实验状态，不把上一轮积累的实现成本当成继续该路线的理由。当前单字问题仍未验收，本研究没有改变这一事实。
- 后续首先做**入口证据调查**：检查可验证的本地化接口/文本所有者与文字缓存生命周期，再选择实现。没有确认写回和恢复条件，就不新增注入分支。
- 保持原初目标：一个 App、框架级 Adapter、共享字典和 Core；必要时允许重启生效。公开接口上的资源/控件处理可以符合这个目标，不必退化成逐游戏词句预设。
