# MV 自带运行器接入实验

## 结论

完整对白入口在真实 MV 引擎中成立。开发运行器通过调试接口接入；普通发布运行器不开放该端口，
但后续已通过原生 V8 导出接口完成接入和中文渲染验证。原生路线目前仅验证一个明确版本的 x86 运行器，
尚未进入生产 Runtime 或验证商业游戏。

用户已安装并打开正版 RPG Maker MV，授权准备和执行测试项目。项目由安装包的新项目模板构造，
加入自行编写的自动对白与选项事件；运行时脚本、素材和本机原始证据保留在本机测试目录。
未加入游戏插件，未修改用户安装目录或既有项目。

## 方法与结果

| 验证 | 结果 |
|---|---|
| MV 自带普通发布运行器，启动时传入 loopback remote debugging 参数 | 游戏进程启动并创建 renderer；指定端口无监听，不能连接 |
| MV 自带开发测试运行器，用相同参数和同一测试项目 | loopback 端口监听成功，页面 CDP 可进入游戏执行环境 |
| 运行时身份 | MV 自报 1.6.1，NW.js 0.29.0，Chromium 65；模板 core 文件头标记 1.6.2，不能只靠文件头判断运行时版本 |
| 完整对白 | 逐字显示之前观测到两行完整原文，仅产生一次整段记录 |
| 首次译文 | 游戏消息字图改变，截图人工复核为完整中文；选择项仍是英文，不在此次适配范围 |
| 另一份译文 | 重新开始测试对白后字图再次改变 |
| 停用 | 当前译文保持不变；下一次对白的字图恢复到原文字图，观测数量不再增长 |
| 游戏源数据 | 运行时原始消息仍为英文；接入前后 44 个项目脚本、元数据与数据文件哈希一致 |

验证使用 [Playwright 合同](../../../../test-support/rpgmaker-mv-text/runtime.spec.cjs)：1 项端到端通过。
[合成合同](../../../../test-support/rpgmaker-mv-text/adapter.test.cjs)：12 项通过。
首次端到端测试发现轮询会读到上一个场景的选项窗口；改为同时等待场景实例更换后验证通过。

原型为兼容 Chromium 65 去除了可选链、空值合并、无绑定 catch 与 `Object.hasOwn`。
未改变文字范围、正式 Native ABI、Runtime Bundle 或产品 Catalog。

## 初次开发运行器实验的边界

- 测试项目使用真实引擎，但不是两个独立商业目标，也没有各种插件改写入口的覆盖证据。
- 没有正式 Native Runtime 桥；此次译文由测试回调提供，不代表 AI 或生产字典链路已经接通。
- 第二份译文和停用恢复都在下一次对白生效，不是当前画面刷新。
- 本次没有修改安装文件，不代表能够附加到未预先开放接口的运行中游戏。
- 调试端口只有本机 loopback。产品若沿用外部协议，仍需解决目标身份校验、会话授权和端口生命周期。

单独实现当前对白安全重绘与停用恢复，再扩大到独立商业目标与其他 NW.js 版本。

官方依据：[NW.js 调试说明](https://docs.nwjs.io/For%20Users/Debugging%20with%20DevTools/)

列出 profile 与 Chromium 参数。文档判断与实测结果一致，但不推导其他版本必然相同。

## 后续原生入口实验：普通运行器已打通

使用原版普通运行器启动同一受控项目，没有 remote debugging 参数、没有 SDK 文件替换。
静态导出调查确认 `nw.dll` 保留具名 V8 接口。通过 Frida 在现有 `v8::Function::Call` 入口的
原线程上取得当前 Isolate 和显式 Context，再调用字符串创建、脚本编译与执行入口。
请求由 HandleScope 与 TryCatch 包围，不保存跨回调的 Local 句柄，也不使用固定地址。
依据：[对应版本 V8 公开头文件](https://github.com/v8/v8/blob/6.5.254/include/v8.h)。

入口实测门槛为 x86、V8 6.5.254.31；对应 NW.js 0.29.0 / Chromium 65。驱动检查授权根进程、
可执行路径、唯一 renderer；执行前再确认 MV 与合成项目标题。其他位数或 V8 版本直接拒绝。
这些检查是实验范围保护，不代表生产版本协商已经完成。

验证结果：

- 在普通运行器原线程中读到 MV 引擎身份，测试游戏进程保持响应。
- 同一 Playwright 端到端合同通过：原文 → 中文 → 另一份中文 → 停用后下一次显示恢复原文。
- 原文保持完整多行；运行中消息源仍是英文；44 个项目脚本和数据文件哈希无变化。
- 两种异常（主动抛错、语法错误）不会破坏后续调用，连续 16 次求值正确。
- 中文渲染快照人工复核通过；原生路径的图像来自引擎 framebuffer，不冒充 OS 窗口截图。
- 合成合同 12 项通过。多轮实验重附加未破坏游戏；最终驱动退出时撤销 Hook。

实验中曾因 Python stdin 使用系统默认编码导致中文表达式损坏；显式 UTF-8 后通过同一合同。
编码与进程选择已纳入可复跑驱动，真实路径、进程值和原始证据不进入跟踪文件。

代码见 [原生入口](../../../../test-support/rpgmaker-mv-text/native-entry.frida.js)、
[测试驱动](../../../../test-support/rpgmaker-mv-text/native-driver.py) 和
[共用画面合同](../../../../test-support/rpgmaker-mv-text/runtime.spec.cjs)。

当时未解决：生产 Runtime 桥、当前对白更新与恢复、选择项、格式控制符、其他位数版本，以及独立商业目标。Runtime 链路的后续结果见下节。
Frida 的高频 JS Hook 只用来证明入口，不能直接作为最终运行时性能方案或随产品打包。

## 正式 Runtime 链路验证

受控普通运行器实测为 Node 9.7.1 / N-API 2。使用该版本的
[官方 Node API 头文件](https://github.com/nodejs/node/blob/v9.7.1/src/node_api.h)
构建仅供测试的 x86 原生桥，头文件下载带固定 SHA-256 校验。
Node 先用 `process.dlopen` 注册桥模块，再由正式 Runtime 根据部署描述和 DLL 哈希加载同一组件。
这一步仍由实验驱动安排，尚未成为正式适配器激活流程。该版本 N-API 标为实验接口，不能推导后续版本 ABI 均兼容。

实际路径为：完整对白 → 原生模块 → Native Text Host → Runtime Kernel / Capture。
译文来自 Rust 生成器创建的正式 publication，不使用 JS 测试字典作为翻译来源。
没有第二套采集队列、字典管理或 AI 系统，也未修改 Native ABI、产品目录或 Bundle。

验证结果：

- 正式 Native Loader 接受桥的描述、ABI、功能授权及工件哈希，激活返回成功。
- 第一代和第二代 publication 返回准确的两份中文，实际消息字图随之变化；中文 framebuffer 人工复核通过。
- 每次完整对白只有一条正式采集记录，批次排空后无重复；第二代发布不重置采集生产者代次。
- 空文本、超长文本、非法事件类型不进入采集。Observe 请求即使命中字典也不返回译文，但保留一次原文采集。
- 只停用 Runtime、保持 JS Hook 安装，后续查询不返回译文；下一次对白字图与接入前原文完全一致。
- 运行中原消息不改写；44 个项目脚本与数据文件哈希不变。
- 原生桥 `/W4 /WX` 构建成功；1 项实际运行器 Playwright 合同、12 项 JS 合成合同通过。
- 后续实际运行器合同增加 12 轮启停：同一部署重复激活成功；旧代次、同代次冲突及无效 JSON 拒绝后，查词仍返回当前正确译文。每轮仅一条采集记录，序号从新生产者起点开始；再次启用的译文字图和停用后原文字图都与基线一致。
- 对照现有控制协议：publication 更新必须严格递增，同代次原样重发也返回 16；重复停止返回未运行状态 15。二者均不应被测试误解为幂等成功；受控测试确认拒绝不破坏后续激活。

接入时发现 Node 与游戏页面都会触发 V8 函数入口。实验驱动现遇到其他执行环境时保留请求，等待正确页面或原有超时，不再提前消费请求。
测试桥入口按正式 ABI 返回结构体值，并提供下一次对白模型的空刷新回调；不是当前画面刷新能力。

该阶段的剩余边界：原生模块注册顺序、无 Frida 的生产调度与版本/会话生命周期；当前对白重绘与恢复；
选项和控制符；多个适配器同时绘制的作用域去重；其他 NW.js 版本与独立商业目标。
原生模块及 Runtime 在测试进程中驻留至退出，行为停用不等于 DLL 安全卸载。

## 去除 Node 先加载的前置条件

对照 [Node 9.7.1 加载器源码](https://github.com/nodejs/node/blob/v9.7.1/src/node.cc)：
`DLOpen` 进入时要求 pending module 为空，在动态库加载后才消费注册结果。
因此 DLL 构造函数在 Runtime 加载线程上调用 `napi_module_register` 并不安全；
重复加载已经驻留的 DLL 也不会重新运行构造函数。

测试桥改为无静态 Node 注册，提供显式注册入口，并在 Node exports 初始化完成前拒绝激活。
实验驱动只在精确匹配桥路径的 `uv_dlopen` 成功返回时调用该入口，注册发生在 Node 消费结果之前。
测试先执行一次未接入 Node 的 Runtime 激活，确认失败回滚；再显式保留 DLL 引用，证明已加载 DLL 仍能被 Node 注册。
Node 注册完成后，正式 Runtime 激活与既有两代字图、单次采集及 12 轮启停合同通过。

第一次实验未命中 `uv_dlopen`，原因为 Frida 的执行回调屏蔽了嵌套 Interceptor。
测试加载改到游戏正常事件循环后通过，不替换 Node 入口、不使用固定地址。
这里的定时回调只安排测试接入，不代表已经实现生产调度或当前对白刷新。

尚待实现：把此窄注册触发器和 V8 请求队列收进原生组件，加入完整版本、页面与会话校验，移除 Frida 依赖。

## 原生会话与无 Frida 测试装载

`native-session.cpp` 已接管 V8 Function::Call 与 Node uv_dlopen 的两个具名入口。
使用固定哈希的 [MinHook 1.3.4](https://github.com/TsudaKageyu/minhook/tree/v1.3.4) 构建，
不复制固定地址或目标函数前几条指令。版本仍严格限定已验证的 x86 V8，执行时再次检查 Node 版本、MV 标识与合成项目标题。

原生队列只有一个待执行请求；空闲回调只检查原子状态。请求在游戏原线程执行，
V8 Local 句柄不跨回调保存；HandleScope、TryCatch 与 UTF-8 转换的构造/销毁成对。
错误页面保持请求待执行，5 秒到期后取消；停止禁用 Hook 并取消排队请求。
跳板和 DLL 保留到进程结束，避免已进入回调的返回路径落到释放内存。

先用只负责控制、不装 Hook 的 Frida 传输验证原生调用约定，再替换为 `remote-driver.cpp`。
最终路线的 Python 驱动只用标准库，未导入 Frida。helper 在同一进程句柄上核对可执行路径、
创建时间、x86 位数；LoadLibrary 的转发目标按实际模块加 RVA 定位，不假设 ASLR 地址相同。
远程命令使用有界数据包，超时不强杀目标线程或释放它可能仍引用的内存。
这些是 fixture 的装载与控制实现，尚未接进产品 Controller。

最终验证：

- 全新受控普通运行器上，正式 Runtime 的两代中文显示、完整原文采集及下一次对白恢复通过。
- 12 轮 Runtime 激活/停止与更新拒绝合同通过。
- 4 轮原生 Hook 会话关闭/再开启通过；关闭期间求值明确拒绝，重新开启后结果正确。
- 切换到合成错误标题触发 5 秒超时；标题由游戏自身事件循环恢复后，过期请求未执行。
- 错误可执行路径、错误创建时间在任何远程装载前被 helper 拒绝。
- 1 项实际运行器 Playwright 合同与 12 项 JS 合成合同通过，中文 framebuffer 可见，项目文件哈希不变。

下一阶段仍需：与现有 Controller 和 Runtime 激活流程整合；将任意求值测试接口换成固定引擎脚本及会话授权；
当前对白刷新/恢复、选择与控制符、多适配器作用域，以及独立商业目标验证。无 Frida 的受控通过不等于已经发布产品支持。

## 固定引擎脚本并入 Runtime 激活

`-ManagedBootstrap` 构建变体将 `adapter.cjs` 的固定内容嵌入同一 DLL，由 `engine-bootstrap.cpp`
根据自己的模块路径接入 Node。Native Adapter 激活先启动原生会话并安装引擎入口，再开放 Host 决策；
不持有文字回调锁等待游戏线程。停用先关闭 Host 决策，再撤销自己的 JS 入口及原生 Hook。
测试不负责安装对白 Hook，只通过正式 Runtime 激活/更新/停止驱动生命周期。

`managed-runtime.spec.cjs` 验证两代译文字图、完整原文及一次采集，4 轮启停后不仅新对白恢复，
`Window_Message.prototype.startMessage` 的函数引用也恢复到接入前的原值。
错误页面导致激活超时返回失败，原生 Hook 与 Runtime 状态回滚；页面恢复后同进程重试成功。
这个合同使用新启动的受控项目，不把“重播测试对白”当成适配器刷新。

新增身份检查过程中发现 CIM 创建时间只有微秒精度，而进程句柄提供 100ns 精度。
发现阶段现读取精确创建时间并核对它落在 CIM 的同一微秒；helper 仍按精确时间严格比较，
未放宽实际目标进程句柄上的身份校验。helper 已退出时，Python 清理不会用管道错误覆盖原始失败。

后续：为固定入口补正式会话绑定和失效处理，接入产品 Controller/打包边界；
实现当前对白的安全重绘与恢复，再验证独立商业目标。测试控制与任意诊断求值仍只留在 test-support。
