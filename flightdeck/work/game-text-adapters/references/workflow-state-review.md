# 工作流与采集状态调查

## 结论与范围

用户报告关闭目标软件、手动刷新工作流后，顶部仍显示运行中。已用本地 Playwright 合成后端响应复现该路径，并通过单独刷新采集缓存的对照确认：工作流刷新与顶部活动徽标没有消费同一份状态。生产代码未修改，也没有重新运行或注入用户目标软件。

顶部徽标汇总全部采集记录，而非当前软件。其他软件确实在运行时，顶部运行中可以成立；截图本身不能排除这个情况。但即使只有一个目标且已退出，现有缓存路径也能独立产生同样误报。

## 状态来源

| 展示/行为 | 当前来源 | 问题 |
| --- | --- | --- |
| 工作流启用开关 | activations / enabledWorkflowIds | 表示持续启用意愿，不能当作进程或翻译正在运行 |
| 工作流列表实际状态 | workflowRuntimeStatus + activations | 使用运行时快照；目标退出且仍启用通常应等待目标 |
| 顶部运行中/已暂停 | useProbeRuns 的全部 runs[].status | 任一旧记录 running 即显示运行中，未绑定最新工作流快照 |
| 采集详情已连接/未连接及按钮 | selectedRun.status | 只轮询当前记录；与其他记录的缓存刷新范围不同 |
| 可直接替换/仅采集 | probe_run_view 的运行时能力投影 | 来自另一运行时缓存；不是采集记录本身的实时进程核验 |
| 自动补全 | 单独读取原生记录摘要 | 不更新顶部使用的前端 runs 缓存 |

## 已证实的链路缺口

1. `App.vue` 向 TitleBar 传 `probe.activityStatus`，`useProbeRuns.ts` 只要缓存中任一记录状态为 running 就显示运行中。
2. `workspace/workflows.ts::refreshWorkflows` 只调用 desktop_refresh_workflows 并 applyDesktopSnapshot；`workspace/state.ts` 仅更新工作区 model，不更新 probe.runs。
3. 后端 refresh_workflows 会更新运行时状态，并通过 update_workflow_collection_status 把失去活动目标的记录改成 Ready。返回的产品快照没有将这些采集摘要同步给前端对应缓存。
4. probe.connect 有 connected 一次性保护。切页面再次 connect 不会重新加载全部记录；详情页每秒仅刷新选中记录。因此主列表手动/五秒刷新完成后，顶部仍可持有旧的 running，多个记录时尤为明显。
5. App.requestNavigation 仅修改 view，没有进入工作流页时立即刷新。此前用户要求的切回刷新尚未落实。
6. 独立每秒采集命令只收取已落盘原文，不检测进程，也不返回更新后的状态，不能承担状态一致性职责。

## 可复现证据

本地 Playwright 脚本模拟一个记录起初 running，随后 desktop_refresh_workflows 返回目标 inactive 并将后端记录改成 ready。执行真实 useWorkspace.refreshWorkflows 后：refreshes=1、记录全量加载=1、顶部仍为运行中。断言徽标消失失败，确认症状可重复捕获。

对照保持相同后端状态，额外调用真实 useProbeRuns.refreshSummary 更新该记录，顶部徽标消失，1 项对照通过。脚本、截图与详细输出仅保存在本地测试区。

这个证据确认前端状态传播缺陷；不等于已验证用户目标软件退出时的全部原生进程回收路径。

## 额外代码风险（尚未实机复现）

- Ready 同时承接未开始、目标失联/退出、停止等多种情况，详情页统一未连接，无法解释“仍启用等待目标”与“用户主动停止”。
- 暂停采集通过同一 status 保存。update_workflow_collection_status 在目标 inactive 时把 Paused 改为 Ready；之后目标恢复又可成为 Running，暂停意愿缺少独立保存边界。
- WorkflowTargetRuntimeView 有 active、translation_active、font_active，却没有独立的采集活动/暂停状态；通用 active 不能完整说明“正在翻译但暂停收集”。
- 运行时快照没有明确的检查时间和未知/过期状态。检查失败后保留的旧画面容易被理解为刚刚确认。

## 建议修复方向

1. 统一工作流运行状态快照。顶部、列表、详情使用同一数据来源及一次更新结果；顶部按实际活动工作流汇总，显示活动数量，消除“当前软件”歧义。
2. 分开保存启用意愿、目标连接状态、翻译活动和采集暂停意愿。推荐展示：已停用、等待软件启动、连接中、运行中、连接失败；暂停收集作为独立标记，不能表示翻译已停。
3. 进入工作流页立即刷新；开始、停止、暂停、恢复、进程退出后同步相关状态。定时检查保留作兜底，合并在途请求，失败标记检查未完成而非继续把旧状态当最新事实。
4. 一次后端刷新同时交付列表与采集状态，或明确发布统一状态事件；无需让各组件各自加定时器。
5. 回归覆盖：单/多软件退出、仅另一个软件存活、主列表手动刷新、切页、暂停后退出重启、断开失败、恢复连接。保留历史原文和独立 AI 任务状态，不用它们推断目标进程是否存活。
